# EV-0011: Next Consumer-Driven Public Surface Selection

## Summary
- EV-0010 validated that Replication Vector's already-owned `Vec<VectorCommand>` data can render through Velumin's browser renderer via the Rust/WASM typed command-slice path, so the current Replication Vector representative frame does not justify another DP-0008 expansion by itself (`project/evidence/EV-0010.md:11-15`).
- A fresh Blasterites pressure check found that its visible game objects are still line/polyline/arc-style vector geometry, but its simulation and drawing are tied to canvas pixel coordinates and full-window wrapping (`JavascriptGames/javascript_games/blasterites/game.js:9-12`, `:288-321`).
- Recommendation: select a narrow DP-0008 follow-up for consumer-owned view/viewport mapping before DP-0007 custom display settings, DP-0003 retained scene/material work, DP-0002 Phase 3/native work, or "no immediate implementation."
- The recommended follow-up should expose browser-first coordinate/view controls sufficient for pixel-space or arbitrary-logical-space consumers to submit `VectorFrame` / `&[VectorCommand]` data without rewriting simulation coordinates into Velumin's fixed centered 4:3 playfield by hand.

## Evidence Reviewed
- Blasterites checkout inspected: `/Users/centaur/Workspace/JavascriptGames/javascript_games` branch `BlasteritesMonolithBranch` at commit `56fc45fa590d0567bf6b6c30c30b85b411ae5bb6`.
- DP-0008 chose immediate-frame submission because arcade-style ships, bullets, rings, debris, and explosions are cheap to rebuild per frame (`project/design/proposals/adopted/browser-vector-frame-api/00_proposal.md:70-82`).
- DP-0008's v1 JavaScript boundary is `VectorFrame` with line, polyline, and closed-polyline methods, while Rust/WASM consumers can keep typed command slices internally (`project/design/proposals/adopted/browser-vector-frame-api/00_proposal.md:83-107`).
- DP-0008 explicitly kept v1 stroke-first and deferred circle/ring helpers until real consumers prove which helpers are worth stabilizing (`project/design/proposals/adopted/browser-vector-frame-api/00_proposal.md:109-122`).
- DP-0008 also chose Velumin's centered 4:3 logical playfield and deferred camera transforms, arbitrary virtual resolutions, and per-frame view controls (`project/design/proposals/adopted/browser-vector-frame-api/00_proposal.md:124-137`).
- DP-0007's adopted v1 only exposes named display presets; custom display settings are explicitly deferred, and preset style is separate from viewport/letterbox policy (`project/design/proposals/adopted/DP-0007-display-preset-public-api.md:21-36`).
- DP-0003 remains a broader proposed scene/layer/material model with layers, transforms, masks, blending, opacity, timing, and multiple material families (`project/design/proposals/proposed/DP-0003-extensible-2d-scene-material-model.md:29-53`).
- DP-0002 keeps the best-practice split: game code owns simulation, frontends own platform lifecycle, and the renderer owns GPU resources (`project/design/proposals/proposed/DP-0002-cross-platform-renderer-architecture.md:52-57`).

## Fresh Consumer Pressure: Blasterites
Blasterites is a current Canvas 2D game rather than a Velumin consumer, but it is a useful pressure point because it resembles the target Asteroids-like browser workload.

- The checked-in game uses a full-window canvas and 2D context directly (`JavascriptGames/javascript_games/blasterites/game.js:9-12`).
- Its simulation state is stored in canvas pixel coordinates: the ship starts at `canvas.width / 2`, `canvas.height / 2`, asteroids spawn against `canvas.width` and `canvas.height`, and screen wrapping uses those same dimensions for ship, asteroid, and bullet positions (`JavascriptGames/javascript_games/blasterites/game.js:150-164`, `:166-205`, `:288-321`).
- Its core visible geometry is compatible with DP-0008's stroke-first model: the ship is a closed path, asteroids are stored as irregular outlines, and the active shield is a circular stroke (`JavascriptGames/javascript_games/blasterites/game.js:729-766`, `:799-818`).
- Bullets and sparks are currently filled arcs (`JavascriptGames/javascript_games/blasterites/game.js:822-837`), but their rendering need is small bright vector marks. They can be approximated by short line bursts or low-segment closed polylines; this is ergonomic pressure for optional helpers, not a blocker for the current primitive set.
- The game loop preserves the DP-0002 ownership split: game code updates ship, asteroid, bullet, collision, and spark state before drawing (`JavascriptGames/javascript_games/blasterites/game.js:1001-1020`). Velumin does not need to own simulation or lifecycle to serve this shape.

The important new pressure is therefore not "Velumin needs retained objects" or "Velumin needs custom glow constants." It is "a browser game with an existing pixel/full-window coordinate model should be able to hand Velumin a frame without scattering ad hoc coordinate conversion throughout game code."

## Options Compared

### Option A: DP-0007 custom display settings
Pros:
- Matches a known deferred API surface: advanced consumers may eventually need arbitrary glow-layer/stroke tuning beyond named presets.
- Keeps visual tuning global to the renderer, consistent with DP-0007's v1 scope.

Cons:
- The fresh Blasterites pressure is coordinate/view compatibility, not a lack of glow presets.
- DP-0007 already states preset style is separate from viewport/letterbox policy, so custom settings would not solve canvas-pixel simulation or wrapping.

Verdict: defer. Useful later, but not the next consumer-driven public surface selected by this evidence.

### Option B: narrow DP-0008 follow-up for view/viewport mapping
Pros:
- Directly addresses the fresh Blasterites pressure: full-window pixel-space simulation and drawing currently depend on `canvas.width`/`canvas.height`, while DP-0008 v1 exposes a fixed centered 4:3 logical playfield.
- Preserves DP-0002's ownership split: game code still owns simulation; Velumin only owns the render-time mapping from consumer coordinates to its renderer viewport.
- Keeps the API immediate-frame and stroke-first; it does not require retained objects, materials, native frontends, or game systems.
- Helps both JS `VectorFrame` and Rust/WASM typed command-slice consumers if expressed as renderer/frame view configuration rather than as a JS-only helper.

Cons:
- It changes a DP-0008 v1 deferred area, so it needs a small follow-up design/work item rather than an ad hoc method addition.
- Care is needed to avoid baking Blasterites' specific full-window wrapping rules into Velumin; the public surface should describe coordinate mapping, not simulation policy.

Verdict: select. This is the next implementation direction most directly grounded in current consumer evidence.

### Option C: DP-0003 retained scene/material model
Pros:
- Long-term model covers layers, transforms, masks, blend modes, opacity, and multiple visual material families.
- Could eventually improve ergonomics for persistent objects, isolated glow layers, and non-vector styles.

Cons:
- Blasterites rebuilds and draws immediate state each frame, which DP-0008 intentionally supports.
- The fresh pressure can be solved with coordinate/view controls without adopting layers, materials, masks, sprites, or timing references.
- Pulling DP-0003 forward now risks scope expansion beyond the browser-first vector frame needs.

Verdict: defer. Keep DP-0003 proposed until consumers need retained/layered/material semantics rather than immediate vector command submission.

### Option D: DP-0002 Phase 3/native `winit`
Pros:
- Important for the eventual Steam/native path and cross-platform renderer validation.
- Would make desktop adapter/capability negotiation concrete.

Cons:
- The fresh consumer pressure is browser-first Blasterites/Replication Vector rendering, not native window lifecycle.
- Native Phase 3 does not resolve the browser coordinate/view mismatch.
- Current focus says Phase 3 awaits its own workstream selection.

Verdict: defer. Valuable horizon work, but not the next public surface for these browser consumers.

### Option E: no immediate implementation
Pros:
- EV-0010 alone supported this option because the current Replication Vector representative frame already renders through `WebGPU::render_commands(&[VectorCommand])`.
- Avoids premature API expansion if no concrete consumer gap exists.

Cons:
- The rechecked Blasterites pressure is concrete and distinct from EV-0010: arbitrary/full-canvas coordinate systems remain awkward against DP-0008's fixed 4:3 logical playfield.
- Deferring all implementation would leave the next consumer adaptation burden in each game rather than in a small, reusable renderer boundary.

Verdict: no longer the best next step. It was correct after EV-0010 alone, but the Blasterites pressure selects a narrow DP-0008 follow-up.

## Recommended Follow-Up Work Item Shape
Create a follow-up implementation work item, tentatively:

`WI-API-0004: Expose Browser Frame View Mapping`

Suggested scope:
- Design and implement a small DP-0008 extension for public view/coordinate mapping on the browser renderer.
- Serve both `VectorFrame` and Rust/WASM `&[VectorCommand]` submissions through the same internal render path.
- Support at least fixed logical 800x600, full-canvas pixel-like coordinates, and/or explicit logical extents, with the exact API settled by a focused proposal/work item.
- Keep wrapping, camera following, simulation, collision, and gameplay out of Velumin.
- Validate with deterministic harness frames that prove the same Blasterites-style frame can be rendered from a non-800x600/full-window-style coordinate model.

Non-goals for that follow-up:
- Do not add custom glow numeric settings.
- Do not add a retained scene graph, materials, sprites, masks, or layers.
- Do not add a native `winit` shell.
- Do not implement Blasterites or Replication Vector gameplay.

## Conclusion
The next consumer-driven public surface should be a narrow DP-0008 view/viewport mapping extension. It has a decisive advantage over the alternatives because it is the only candidate that directly addresses both the existing DP-0008 deferred area and the fresh Blasterites pressure point while preserving Velumin's browser-first, renderer-owned-GPU, game-owned-simulation architecture.

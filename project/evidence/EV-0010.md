# EV-0010: DP-0008 Replication Vector Consumer Browser Validation

## Summary
- Validated the motivating Replication Vector downstream case against DP-0008's Rust/WASM typed command-slice path.
- A temporary browser harness called `replication_vector::first_replication_vector_scene()` to obtain Replication Vector-owned `Vec<VectorCommand>` data, then rendered that slice through `WebGPU::render_commands(&[VectorCommand])` without rebuilding it through JavaScript `VectorFrame`.
- Browser runtime capture succeeded on a WebGPU-capable Chromium: 4 commands rendered to a nonblank 1024x768 canvas with visible vector geometry.
- Recommendation: no immediate DP-0008 public API expansion is justified by this representative frame. The typed Rust/WASM command-slice path is sufficient for the current Replication Vector scene; future API work should wait for additional consumer pressure or separately pursue DP-0007 custom display settings / DP-0003 retained scene design if those needs become concrete.

## Source Facts
- Replication Vector imports Velumin command/style types directly and defines `first_replication_vector_scene() -> Vec<VectorCommand>` (`ReplicationVector/replication_vector/replication_vector/src/lib.rs:3`, `:60`).
- The representative scene contains a parent probe polyline, asteroid polyline, shield-arc polyline, and projectile line (`ReplicationVector/replication_vector/replication_vector/src/lib.rs:60-99`).
- Replication Vector's earlier downstream evidence recorded the former gap: project-owned command data existed, but direct browser rendering through Velumin was not yet proven (`ReplicationVector/replication_vector/project/evidence/EV-0004.md:29-38`).
- Velumin's Rust/WASM path renders already-owned command slices through the normal renderer path, resizing the canvas and calling `self.renderer.render(commands, false)` (`webgpu_vector_lib/src/lib.rs:718-728`).
- The current Replication Vector browser page still exposes only the command-count harness (`ReplicationVector/replication_vector/replication_vector/web/index.html:52-60`), so the runtime render validation used a temporary harness instead of changing the downstream repo.

## Browser Runtime Harness
The temporary Rust/WASM harness depended on Replication Vector and the same Velumin checkout used by Replication Vector. Its exported render function did the important part:

```rust
let commands = replication_vector::first_replication_vector_scene();
let mut gpu = WebGPU::create(canvas_id).await?;
gpu.render_commands(&commands)?;
```

This keeps the boundary under test as typed Rust/WASM `&[VectorCommand]`: JavaScript only loaded the temporary wasm module and waited for `window.__smokeReady`; it did not serialize commands into JavaScript or rebuild them through `VectorFrame`.

## Gap Assessment
- **Typed Rust/WASM command-slice path:** sufficient for one representative Replication Vector frame. No Velumin public API change is required to render the current project-owned command slice.
- **JavaScript `VectorFrame` boundary:** not involved in this validation. This is good: the motivating Rust/WASM consumer did not need to serialize typed commands into JavaScript and rebuild them back into Rust.
- **Camera/view controls:** no immediate gap for the representative frame. Replication Vector's coordinates already fit Velumin's centered 4:3 logical playfield.
- **Batching/capacity reuse:** no actionable gap from this frame. The representative scene has four commands, so it does not create evidence for reservation, persistent buffers, or batching controls.
- **Ring helpers:** the current shield arc is representable as a polyline. A helper could be useful ergonomically later, but this validation does not justify adding one to Velumin's v1 public API.
- **Display settings:** the default renderer settings produced visible output. DP-0007 custom display settings remain a separate possible direction, not a blocker for this consumer frame.
- **WASM packaging friction:** the downstream baseline passes with its `.deps/velumin` checkout. The temporary harness needed to use the same `webgpu_vector_lib` path as Replication Vector to keep `VectorCommand` types identical, and needed the existing `wasm-bindgen` 0.2.121 toolchain rather than resolving a newer temporary dependency. This is validation-harness friction, not a Velumin API blocker.
- **Replication Vector web integration:** the downstream repo's checked-in web page still only reports command count. Wiring an actual Replication Vector browser page to render the typed command slice is downstream integration work, not evidence that Velumin needs a new public surface.

## Conclusion
WI-API-0002 closes the evidence loop opened by Replication Vector's `EV-0004`: direct browser rendering of downstream-owned scene data through Velumin is now proven for the representative frame. The next Velumin public-surface decision should not be an automatic DP-0008 expansion; use additional consumer evidence before adding capacity controls, helpers, retained scene/material APIs, or custom display settings.

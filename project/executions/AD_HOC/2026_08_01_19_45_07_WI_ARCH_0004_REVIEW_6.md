# Result

Finding `r3696473860` (P2) — Required Change 1 cited `Renderer::new` alone
as the location of the completed web-side adapter/capability negotiation,
but `Renderer::new` receives an already-acquired `wgpu::Adapter` parameter
and only validates its capabilities; it does not request/acquire the
adapter. Verified directly: `sed -n '410,445p' webgpu_vector_lib/src/lib.rs`
shows `Renderer::new(surface, adapter: &wgpu::Adapter, ...)` performing
only format/alpha-mode/present-mode/limits checks against the passed-in
adapter. `sed -n '280,345p'` on the same file shows
`WebGPU::create_with_preset` performing `instance.request_adapter(...)`
(lines ~327-337) with its own "Failed to get a WebGPU adapter" error
handling — the actual adapter acquisition. Independently confirmed against
`project/work_items/resolved/WI-ARCH-0003.md`'s own Problem/Context
section, which already documents this exact split explicitly ("`WebGPU::
create_with_preset` acquires the `wgpu::Adapter` itself... before ever
calling `Renderer::new`"). Genuine finding, not a misreading — citing
`Renderer::new` alone for the whole "adapter/capability negotiation"
bullet left half of it (adapter acquisition) undocumented.

Fixed by requiring Required Change 1 to cite both functions: `WebGPU::
create_with_preset` for adapter acquisition, `Renderer::new` for
capability validation, as together constituting the completed web-side
negotiation. Mirrored the same detail into the Acceptance Criteria and
frontmatter `acceptance:` entries. Replied to the GitHub comment
referencing the fix commit.
